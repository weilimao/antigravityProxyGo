## 修复 WorkBuddy 中继 400 / code 11128（Illegal API invocation from an unapproved channel）

**现象**：Claude Code v2.1.261（API Usage Billing）把模型设为 `workbuddy/intl/deepseek-v4.1-flash[1M]`，发一句 "hi" 即返回 400 + code 11128，提示 "failed channel verification / not from an official client"。

**根因**（代码定位）：
- `internal/relay/workbuddy.go` 里 `convID := sessionKey`，把内部会话键（`claude:<uuid>` / `acc:<id>` / `auth:acc:` / `sock:acc:`）直接写进上游 `X-Conversation-ID`。上游要求标准 UUID，且 `claude:` 前缀本身就是"非官方客户端"的最强指纹 → 渠道校验失败。
- 上游请求缺 `X-Current-Account-Id`（官方桌面端与 `X-User-Id` 同值，checkin 流程 `account_workbuddy_checkin.go` 有带）。
- 系统提示指纹清洗是关键词黑名单，漏网的 `claude` / `anthropic` 残留仍会被判定非官方客户端。

**改动**：
- 新增 `internal/relay/workbuddy_ids.go`：`workbuddyConversationID()` 把任意会话键规整为 UUID——裸 UUID 小写复用，否则 SHA-256 派生确定性 UUID v4（保持 sticky 会话语义，且不泄露前缀）。
- `workbuddy.go`：改用 `workbuddyConversationID(sessionKey)`；补 `X-Current-Account-Id`；更新文件头注释。
- `workbuddy_sanitize.go`：新增 `sanitizeWorkBuddySystemText()`，system 消息在通用清洗后再泛化残留 `\bclaude\b` / `\banthropic\b`（仅 system，不污染用户正文）；补充 `claude.ai/code`、`@anthropic-ai/` 两个客户端固定引用。
- 测试：新增 `workbuddy_ids_test.go`（UUID 格式/确定性/裸 UUID 透传/空值随机），`workbuddy_sanitize_test.go` 追加 2 例，`workbuddy_test.go` 端到端断言 `X-Conversation-ID` 为合法 UUID 且无前缀、`X-Current-Account-Id` 存在。

**验证**：`go build ./...` 通过；`go test ./internal/relay/ ./internal/account/ ./internal/modelfetch/` 全绿。

**注意**：仓库现有 .go 文件为 CRLF，`gofmt -l` 会全量列出（历史现象，非本次改动引入）；新文件为 LF 且 gofmt 干净。重建用 `build.bat`。

## 第三轮：实证定位——11128 是「账号级」问题，不是请求内容

**用户提问**：模型测速能用，为什么聊天被拦。

**实测**（直接打 18444 中继，用测速内置令牌 `sk-ant-benchmark-internal-probe-...`，每次 max_tokens 16~64）：
- 极简请求 ×7：全 200。
- 长 system（15k 字符）+ 15 个 Claude Code 工具 + thinking + max_tokens 32000（Anthropic 与 OpenAI 两种入站协议）：全 200。
- 结论：**请求头、system prompt、工具定义、thinking 都不是触发点**。

**重新读用户日志**：18:09:59 那条 400 的 token 是 `sk-ant-benchmark-internal-probe`、路径 `/route/v1/chat/completions`——那是**测速/自动探针**，不是 Claude Code；且落在 `weilimao95@gmail.com`，而同一时刻极简探针在其它账号上能通。

**结论**：11128 是**账号级**渠道校验失败（该账号令牌/渠道被上游标记），同一 payload 换号即可通过。旧策略「不冷冻 + 立即把错误抛给客户端」导致被标记账号一直留在轮询里，用户侧表现为"时好时坏、测速能通聊天被拦"。

**改动**（`internal/relay/workbuddy.go`）：
- 新增常量 `workbuddyChannelBlockCooldownMs = 10min`。
- 11128 分支重写：只要还有其它可用账号 → 对该账号按 workbuddy 渠道隔离 10 分钟（`Cooldowns["workbuddy"]`，workbuddy 的 category 与模型无关，等于全模型隔离）并换号重试；只剩最后一个账号时不隔离，避免上游整体故障冻死整池。
- 记录 `lastBlockStatus/lastBlockBody`，全部账号都 11128 时回传上游原始错误而非笼统 502。
- 测试：`TestWorkBuddy_11128_NoCooldownAndNoPoolExhaustion` 改写为 `TestWorkBuddy_11128_QuarantineAndFailover`（断言换号 2 次、首个账号被隔离、最后一个不隔离）；新增 `TestWorkBuddy_11128_FailoverSucceeds`（坏号→好号，客户端拿到 200 + 正常内容）。

**验证**：`go build ./...` 通过；relay/account 测试全绿。

## 第四轮：从官方客户端 app.asar 里扒出真实请求头（决定性）

用户提示"直接抓 workbuddy 本身的请求对照"。做法：本机装了 `E:\WorkBuddyCN`（Electron），直接读 `resources/app.asar`（96MB）里的 JS 字符串，找到官方 chat 请求构造：

```
Accept: text/event-stream, Content-Type: application/json, Authorization: Bearer <token>
X-Request-ID / X-Conversation-ID / X-Conversation-Request-ID / X-Conversation-Message-ID
X-IDE-Type: WorkBuddy, X-IDE-Name: WorkBuddy, X-IDE-Version: <app 版本>
X-Product: SaaS, X-Private-Data: true
X-Agent-Intent: craft, X-Agent-Purpose: conversation
x-codebuddy-request: 1        ← 官方 app-server 安全头（applyWorkbuddyAppServerSecurityHeader）
traceparent / b3 / X-B3-TraceId / X-B3-ParentSpanId / X-B3-SpanId / X-B3-Sampled / X-Trace-ID
```

**我们的差距**（这就是 11128 的真因）：缺 `x-codebuddy-request`、`X-Agent-Purpose`、全部 B3 追踪头；`X-Product` 写成 WorkBuddy（官方 SaaS）；`X-Private-Data` 写成 false（官方 true）。另外官方请求体**不含** `extra_vars/growthEvent`（前一轮的猜测是错的，已从链路摘除）。

**改动**（`internal/relay/workbuddy.go`）：
- 新增 `applyWorkBuddyChatHeaders()`：一次性设置上述全部官方头 + 生成 `traceparent`/`b3`/`X-B3-*` 链路追踪头（`workbuddyRandomHex`）。
- 11128 策略回退为**不冷冻账号**（实测整池都会拒 → 冷冻会冻死整池），仅本请求内跳过并换号；全部失败时回传上游原始错误。
- 新增 `workbuddyDumpBlockedPayload()`：被拦时把上游载荷落盘到临时目录，便于后续逐字节比对。
- 测试同步：端到端断言 `x-codebuddy-request=1`、`X-Agent-Purpose=conversation`、`X-Private-Data=true`、`X-Product=SaaS`、`traceparent` 合法；11128 测试改为断言"换号 2 次且不冷冻"。

**方法沉淀**：以后遇到"上游判定非官方客户端"，直接 `grep app.asar` 找官方请求构造，比抓包快且无 TLS 障碍。

## 第五轮：实证锁定真凶——system prompt 里的字面句式指纹（`Main branch (you will usually use this for PRs)`）

**现象**：第四轮补齐官方头后仍 11128；`C:\Temp\wb11128_*.json` 一晚上堆了 83 份同尺寸（68109B）载荷，说明**同一份载荷在整池每个账号上都被拒**。

**决定性实验**（不走中继，直接打 `https://www.workbuddy.ai/v2/chat/completions`，用 `D:\antigravityProxy\data\accounts_workbuddy.json` 里的真实 token + 复刻的官方头，脚本 `C:\Temp\probe_wb.py` / `bisect_wb.py`）：
- 极简载荷（system "You are a helpful assistant." + "hi"）→ **200**。⇒ 账号、token、请求头、TLS 全部无辜。
- 原样被拦载荷 → **11128**（稳定复现）。
- 去 tools / 去 reasoning_effort / 换 max_tokens → 仍 11128；只留 system+hi → 仍 11128；只留 user 消息（最小 system）→ **429（已过渠道校验）**。⇒ 触发点在 **system prompt**。
- 对 system 做字符区间二分：`[4155:6230]` 200 / `[6230:8310]` 11128 → `[6480:6730]` 11128 → 最终最小触发串 = **`Main branch (you will usually use this for PRs)`**。

**坑**：`SYS.index("Status:")` 会命中 `gitStatus:` 内部的 `Status:`，导致切片为空、误判"gitStatus 段无害"（第一次差点被误导）。

**改动**：
